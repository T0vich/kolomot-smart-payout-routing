# Умный роутинг выплат — команда «Коломот»

Хакатон, кейс **«Задача 2. Умный роутинг выплат»**.
Движок распределяет выплаты между платёжными провайдерами: отбирает допустимых
по жёстким ограничениям, выбирает лучшего по совокупности бизнес-целей,
при отказе переходит к следующему, а по итогам прогона объясняет каждое решение
и даёт рекомендации по настройке роутинга.

**Команда:** Фёдор Филитович, Артём Корсаков.
**Язык:** Ruby 3.3, только стандартная библиотека — внешних гемов нет,
`bundle install` не нужен.

---

## Быстрый старт

```bash
rake route      # прогон публичной очереди из 10 заявок
rake validate   # валидатор организаторов поверх результата
rake test       # юнит-тесты
```

Или напрямую, без rake:

```bash
ruby bin/route --queue data/operations_queue_10.json \
               --providers data/providers.json \
               --config config/routing.yml \
               --decisions routing_decisions.json \
               --report routing_report.json
```

## Сдаваемые артефакты

За час до стопкода организаторы дают `operations_queue_test.json`.
Оба требуемых файла генерируются одной командой:

```bash
cp <выданный файл> data/operations_queue_test.json
rake submit
```

В корне репозитория появятся `routing_decisions_test.json` и
`routing_report_test.json`. Полный регламент сдачи — в [TASKS-ARTEM.md](TASKS-ARTEM.md).

## Как устроено решение

Пайплайн одной заявки:

```
                      ┌─────────────────────────────────────┐
   operation ────────▶│ 1. Hard-constraints                 │
                      │    «можно ли вообще отправить?»     │
                      └───────────────┬─────────────────────┘
                                      │ допустимый пул
                      ┌───────────────▼─────────────────────┐
                      │ 2. Soft-goals (7 стратегий)         │
                      │    каждая даёт под-скор [0..1]      │
                      └───────────────┬─────────────────────┘
                      ┌───────────────▼─────────────────────┐
                      │ 3. Композитный скоринг              │
                      │    взвешенная сумма + разрешение    │
                      │    ничьи по порядку политик         │
                      └───────────────┬─────────────────────┘
                      ┌───────────────▼─────────────────────┐
                      │ 4. Каскад попыток → fallback        │
                      │    отказ ⇒ следующий кандидат,      │
                      │    пул пуст ⇒ self-provider         │
                      └───────────────┬─────────────────────┘
                      ┌───────────────▼─────────────────────┐
                      │ 5. Обновление состояния пула        │
                      │    лимиты, обороты, интенсивность   │
                      └─────────────────────────────────────┘
```

**Ключевое разделение:** жёсткие ограничения (допуск) и мягкие цели
(предпочтение) — это разные слои. Hard-constraints применяются до выбора
стратегии и не могут быть нарушены никогда. Soft-goals работают только внутри
уже допустимого пула.

### Hard-constraints

Статус провайдера, диапазон суммы чека, дневной лимит, лимиты одновременных
заявок по количеству и сумме, фильтр по банку, маржа, наличие реквизитов,
лимит интенсивности. Каждый — отдельный класс в `lib/smart_routing/constraints/`,
включается и настраивается через `config/routing.yml`.

### Soft-goals

Семь стратегий из ТЗ, каждая нормирует свой сигнал в `[0..1]`:

| # | Стратегия | Поле | Что делает |
|---|---|---|---|
| 1 | Доля по количеству | `traffic_percentage` | минимизирует отклонение фактических долей от целевых |
| 2 | Доля по объёму | `volume_share_pct` | то же, но по рублям |
| 3 | Каскад | `priority` | последовательный обход по приоритету |
| 4 | По сумме чека | `amount_bands` | диапазон суммы влияет на предпочтение, а не только отсекает |
| 5 | По конверсии | `conversion_24h` | предпочитает более успешных |
| 6 | По интенсивности | `requests_per_minute_limit` | учитывает текущую загрузку, а не только факт достижения лимита |
| 7 | Фин. обязательства | `daily_turnover_min/max` | дотягивает минимальный оборот, притормаживает у максимума |

### Разрешение конфликта целей

Цели конфликтуют — это нормально и заложено в ТЗ. Мы решаем так:

1. **Скоринг.** Итоговый балл — взвешенная сумма нормированных под-скоров.
   Веса задаются в конфиге, а не в коде.
2. **Ничья.** Если разрыв между лидерами меньше `tie_break_epsilon`,
   применяется явный порядок политик: **фин. обязательства → целевые доли →
   конверсия → объём → каскад → диапазон суммы → загрузка.**
   Обязательство по обороту выше долей, потому что за него платят деньгами
   по договору, а доля — целевой ориентир.
3. **Цель недостижима.** Если требуемая доля относится к провайдеру, который
   сейчас недоступен по hard-constraints, цель не блокирует роутинг: заявка
   уходит следующему кандидату, а расхождение фиксируется в отчёте
   с рекомендацией.

### Объяснимость

В `routing_decisions.json` для каждой заявки лежит массив `attempts` со всеми
рассмотренными провайдерами: у выбранного — причина выбора и разложение скора
по слагаемым, у остальных — конкретная причина исключения
(`amount_exceeds_limit`, `bank_not_in_list`, `lower_score`, …) и человекочитаемая
расшифровка в `details`.

## Структура репозитория

```
bin/            точки входа: route, analyze, validate
config/         routing.yml — все правила, веса и пороги
data/           исходные данные кейса
docs/           архитектура, стратегии, журнал решений, ответы жюри
lib/            ядро решения
scripts/        validate_10.rb — валидатор организаторов, как есть
test/           юнит-тесты (minitest, без внешних зависимостей)
```

Внутри `lib/smart_routing/`:

```
config.rb            загрузка и валидация конфига, профили роутинга
provider_pool.rb     состояние провайдеров, модельное время, агрегаты долей
rate_limiter.rb      скользящее окно интенсивности
router.rb            оркестрация: фильтр → скоринг → каскад → fallback
simulator.rb         детерминированная симуляция исхода и задержки
constraints/         жёсткие ограничения, по классу на правило
strategies/          мягкие цели, по классу на стратегию
scoring/             композитный скоринг и разрешение ничьи
analytics/           калибровка по истории, отчёт, рекомендации
models/              operation, provider, attempt, decision
```

## Расширяемость

- **Новый провайдер** — строка в `providers.json`, код не меняется.
- **Новое правило допуска** — класс в `constraints/` + запись в реестр и конфиг.
- **Новая стратегия** — класс в `strategies/` + вес в конфиге.
- **Другая политика роутинга** — новый профиль в `config/routing.yml`,
  переключается флагом `--profile`.

## Ограничения кейса

Никаких проприетарных решений, никаких нейросетей в рантайме: весь выбор
провайдера — детерминированные правила и арифметика, воспроизводимые
при повторном запуске.
