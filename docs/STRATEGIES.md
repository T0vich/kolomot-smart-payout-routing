# Стратегии распределения

Семь стратегий из ТЗ. Каждая — отдельный класс, каждая возвращает
под-скор в `[0..1]` по всем кандидатам сразу, каждая включается весом
в профиле `config/routing.yml`.

Вес `0` или отсутствие ключа = стратегия не участвует в прогоне.

---

## 1. Доля по количеству заявок — `traffic_share`

**Поле:** `traffic_percentage`
**Класс:** `strategies/traffic_share.rb`

Наивный вариант «отдать тому, у кого меньше заявок» ломается, как только
провайдеров становится больше двух или часть из них недоступна.

Мы считаем иначе: для каждого кандидата вычисляем, каким станет **суммарное
отклонение всех фактических долей от целевых**, если заявку отдать именно ему.
Меньше отклонение — выше балл.

```
error(c) = Σ | share_after(p, c) − target(p) |
```

На длинной дистанции это сходится к целевым долям точно: тест
`test_distribution_follows_traffic_targets` проверяет, что 10 заявок
при целях 60/40 распределяются как 6/4.

## 2. Доля по объёму — `volume_share`

**Поле:** `volume_share_pct` (задаётся в конфиге, при отсутствии берётся
`traffic_percentage`)
**Класс:** `strategies/volume_share.rb`

Та же математика, но доли считаются в рублях. Крупная заявка сильнее двигает
распределение, чем мелкая — именно этого и ждут от стратегии «процент от объёма».

## 3. Очередь в каскаде — `cascade_priority`

**Поле:** `priority`
**Класс:** `strategies/cascade_priority.rb`

Ранг считается **среди доступных кандидатов**, а не по всему списку. Если
провайдер с `priority: 1` отсеян hard-constraints, первым в каскаде становится
следующий и получает полный балл. Профиль `cascade` (вес 1.0) даёт классический
последовательный обход, как депозиты в проде.

## 4. По сумме чека — `amount_band`

**Поле:** `amount_bands` в конфиге
**Класс:** `strategies/amount_band.rb`

Принципиальное отличие от hard-constraint `amount_range`: там сумма определяет
**допуск**, здесь — **предпочтение**. Провайдер вне «своего» диапазона остаётся
допустимым, просто получает `miss_score` вместо `match_score`.

```yaml
amount_bands:
  - { from: 0,      to: 50000,  prefer: [payflow] }
  - { from: 50001,  to: 100000, prefer: [vipay] }
  - { from: 100001, to: null,   prefer: [quickpay] }
```

## 5. Приоритизация по конверсии — `conversion`

**Поле:** `conversion_24h`, опционально смешанное с историей
**Класс:** `strategies/conversion.rb`

Эффективная конверсия — смесь заявленной и фактической:

```
effective = conversion_24h × (1 − history_blend) + observed × history_blend
```

По умолчанию `history_blend: 0.3`. Это не случайность: в кейсе заявленная
конверсия расходится с фактической очень сильно — у `payflow` 0.91 против
0.47 по истории (`rake analyze`). Полностью доверять снимку нельзя,
полностью истории — тоже, она за один день.

Разброс конверсий узкий (0.79–0.91), поэтому сигнал нормируется относительно
текущих кандидатов, иначе он не влияет ни на что.

## 6. По интенсивности — `load_balance`

**Поле:** `requests_per_minute_limit` + текущее состояние лимитов
**Класс:** `strategies/load_balance.rb`

Загрузка здесь именно **влияет на выбор**, а не только проверяется на
достижение потолка (жёсткая часть живёт в `constraints/rate_limit.rb`).
Балл считается по самому узкому месту провайдера:

```
load = max(дневной оборот, in-progress count, in-progress amount,
           занятые реквизиты, заявок в минуту)
score = 1 − load
```

## 7. Фин. обязательства — `turnover_commitment`

**Поля:** `daily_turnover_min`, `daily_turnover_max` (конфиг)
**Класс:** `strategies/turnover_commitment.rb`

Гейт часто выдают на условиях «не менее X ₽/сутки»; недобор стоит денег.
Шкала намеренно разрывная:

* `[0.6 .. 1.0]` — минимум ещё не набран, чем больше недобор, тем выше балл;
* `[0.0 .. 0.5]` — минимум закрыт, балл падает по мере приближения к максимуму.

Разрыв между 0.5 и 0.6 гарантирует, что провайдер с невыполненным
обязательством всегда предпочтительнее того, у кого обязательств нет.

## Профили

| Профиль | Что делает |
|---|---|
| `balanced` | Все семь целей вместе. Сдаваемый по умолчанию |
| `cascade` | Чистый каскад по `priority` |
| `traffic` | Только доли по количеству |
| `volume` | Доли по объёму (75%) + по количеству (25%) |
| `conversion_first` | Максимизация успешности, доли вторичны |
| `commitments` | Приоритет фин. обязательств |
| `demo_failover` | Демонстрация каскада и fallback (отказы включены) |

Сравнить их на одних и тех же данных: `rake compare` и `rake compare BACKTEST=1`.

**Наблюдение по публичной очереди.** Все содержательные профили дают
одинаковое распределение: 4 из 10 заявок безальтернативны по
hard-constraints, а на остальных шести сигналы стратегий указывают на одного
и того же провайдера. Расхождение видно на большом объёме — на 100
исторических операциях `balanced` даёт отклонение 26 п.п. при ожидаемой
конверсии 0.66, а `conversion_first` — 38 п.п. при 0.69. Это и есть тот самый
конфликт целей в числах: соблюсти доли или максимизировать успешность.
