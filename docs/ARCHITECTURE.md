# Архитектура решения

## Зачем такое разделение

В задаче смешаны два разных вопроса, и большинство ошибок берётся из того,
что их решают одним механизмом:

1. **Можно ли вообще отправить эту заявку этому провайдеру?**
   Ответ бинарный, нарушать нельзя никогда — это hard-constraints.
2. **Кого из тех, кому можно, выбрать?**
   Ответ — предпочтение, и оно всегда компромисс между конфликтующими
   целями — это soft-goals.

Поэтому в коде это два независимых слоя. Стратегия не может «уговорить»
роутер нарушить лимит, а жёсткое ограничение ничего не знает про доли и
конверсию.

## Пайплайн одной заявки

```
operation
   │
   ▼
ProviderPool#advance_clock ──── освободить in-progress по завершившимся заявкам
   │
   ▼
Constraints::Chain ──────────── 9 правил допуска, первое сработавшее отсеивает
   │                            каждый отсев сразу пишется в attempts
   ▼  допустимый пул
Strategies (7 штук) ─────────── каждая даёт под-скор [0..1] по всем кандидатам
   │
   ▼
Scoring::CompositeScorer ────── взвешенная сумма + разрешение ничьи
   │
   ▼  ранжированный список
Router#walk_cascade ─────────── попытка → отказ → следующий кандидат
   │
   ▼  никто не принял
Router#fall_back ────────────── self-provider (spacepayments)
   │
   ▼
Simulator#outcome ───────────── approved / rejected / expired + задержка
   │
   ▼
ProviderPool#occupy ─────────── занять слот, зарезервировать лимит, записать интенсивность
```

## Модули

| Файл | Ответственность |
|---|---|
| `config.rb` | Загрузка `routing.yml`, профили, валидация. Единственное место, где решается «что включено» |
| `provider_pool.rb` | Состояние провайдеров, модельное время, агрегаты долей |
| `rate_limiter.rb` | Скользящее окно 60 секунд для стратегии по интенсивности |
| `constraints/` | По классу на правило допуска. Реестр в `registry.rb` |
| `strategies/` | По классу на мягкую цель. Реестр в `registry.rb` |
| `scoring/` | Композитный балл и явное разрешение конфликта целей |
| `router.rb` | Оркестрация: фильтр → скоринг → каскад → fallback → обновление состояния |
| `simulator.rb` | Детерминированная симуляция исхода |
| `analytics/` | Калибровка по истории, отчёт, backtest, сравнение профилей, дашборд |
| `models/` | Operation, Provider, Attempt, Decision |

## Учёт лимитов: резервирование, а не пост-фактум

Наивная реализация увеличивает `daily_approved_amount` только после
подтверждения выплаты. Тогда десять заявок, отправленных подряд, все
проходят проверку дневного лимита — и лимит оказывается продан несколько раз.

Мы резервируем сумму в момент выбора провайдера:

```
занятый лимит = daily_approved_amount + daily_reserved_amount
```

Когда заявка завершается, резерв снимается: при `approved` сумма переезжает
в `daily_approved_amount`, иначе просто освобождается. Тот же принцип для
`in_progress_count` и `in_progress_amount`.

Побочный эффект приятный: наша проверка всегда строже проверки валидатора
организаторов, который считает по исходному снимку. Значит, выбранный нами
провайдер гарантированно входит в его список допустимых.

## Модельное время

`in_progress` не может только расти: заявка занимает слот на `latency_sec`
и освобождает его. Роутер двигает часы по `created_at` очередной заявки и
списывает всё, что успело завершиться. Это и реалистично, и нужно для
корректной работы лимитов на длинной очереди.

## Разрешение конфликта целей

Формализовано в три шага:

1. **Композитный балл.** `score = Σ (под-скор × вес) / Σ вес`.
   Веса — в конфиге, не в коде.
2. **Ничья.** Если разрыв ≤ `tie_break_epsilon`, применяется явный
   `conflict_order`. По умолчанию: фин. обязательства → доли по количеству →
   конверсия → доли по объёму → каскад → диапазон суммы → загрузка.
3. **Полное равенство.** Детерминированный рубеж: `priority`, затем имя.
   Один и тот же вход всегда даёт один и тот же выход.

Если цель недостижима — например, целевая доля относится к провайдеру,
которого сейчас отсекают hard-constraints, — она не блокирует роутинг.
Заявка уходит следующему кандидату, а расхождение попадает в отчёт
с конкретной рекомендацией.

## Нормировка под-скоров

Часть сигналов имеет абсолютный смысл, часть — только сравнительный:

* **Сравнительные** (`traffic_share`, `volume_share`, `conversion`,
  `cascade_priority`) нормируются min-max по текущим кандидатам.
  Иначе разница конверсий 0.79 против 0.91 тонет в остальных слагаемых.
* **Абсолютные** (`load_balance`, `turnover_commitment`, `amount_band`)
  считаются по своей шкале: «загружен на 64%» осмысленно само по себе.

Следствие, которое стоит знать: при двух кандидатах сравнительные стратегии
дают ровно 1.0 и 0.0, и выбор превращается во взвешенное голосование.

## Модель отказа

Различаем два события, которые в ТЗ названы одним словом:

* **Провайдер не принял заявку** — ретраибельный отказ, роутер идёт
  к следующему кандидату, а если их не осталось — к self-provider.
* **Провайдер принял и обработал** — терминальный исход
  (`approved` / `rejected` / `expired`), маршрут уже не меняется.

Искусственные отказы первого рода в сдаваемом профиле выключены: прогон
должен быть воспроизводимым, а `reference_decisions.json` требует для
безальтернативных заявок строго определённого провайдера. Механика каскада
от этого не исчезает — она включается профилем `demo_failover`
(`rake demo`) и покрыта тестами `test/router_test.rb`.

## Расширение

* **Новый провайдер** — строка в `providers.json`. Код не меняется.
* **Новое правило допуска** — класс в `constraints/`, строка в `Registry::ALL`,
  ключ в `constraints:` конфига.
* **Новая стратегия** — класс в `strategies/`, строка в `Registry::ALL`,
  вес в профиле.
* **Другая политика** — новый профиль в `routing.yml`, флаг `--profile`.
