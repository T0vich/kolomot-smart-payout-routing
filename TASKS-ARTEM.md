# Артём — план работ

Команда **Коломот**. Кейс: «Задача 2. Умный роутинг выплат».
Фёдор пишет ядро роутинга (`lib/`), твоя зона — всё, что вокруг: чекпоинты,
защита, документация и независимая проверка.

Короткий контекст: 100 баллов ставят эксперты по итогам 3 чекпоинтов,
140 — техжюри на защите, 20 — отраслевое жюри за выступление и полноту.
Из 140 баллов техжюри **40 — просто за два файла в корне main**.

---

## 0. Первое, что нужно сделать (5 минут)

1. Принять инвайт в репозиторий на GitHub.
2. `git clone` и прочитать `README.md` + `docs/ARCHITECTURE.md`.
3. Прочитать `docs/case-description.docx` — исходное ТЗ организаторов.
4. Проверить, что у тебя есть Ruby: `ruby -v`. Нужна версия **3.3+**.
   Если нет — поставь через `rbenv`/`asdf` или системный пакет.
   Внешних гемов в проекте нет, `bundle install` не нужен.
5. Запустить прогон и убедиться, что всё работает:
   ```
   rake route      # прогон публичной очереди из 10 заявок
   rake validate   # прогон валидатора организаторов
   rake test       # юнит-тесты
   ```

## 1. Вопросы жюри на предварительной QA-сессии

Список готов. Задать **все**, особенно первый — от него зависит,
не дисквалифицируют ли нас.

1. «Запрещено использование нейросетей внутри проекта» — это про рантайм решения
   (никаких ML-моделей в самом роутинге), или в том числе про использование
   ИИ-ассистентов при написании кода?
2. `simulated_result: "rejected"` — это отказ, после которого надо
   перемаршрутизировать на следующего провайдера, или терминальный исход уже
   принятой заявки? В ТЗ «при отказе перейти к следующему», но
   `reference_decisions.json` требует для `op_103` строго `quickpay`,
   а он там единственный допустимый.
3. Если единственный допустимый провайдер отказал — `selected_provider` должен
   смениться на `spacepayments`, или остаться тем, кто реально обрабатывал?
4. `validate_10.rb` считает eligible по **исходному** `providers.json`, не обновляя
   состояние. А ТЗ требует «после каждой заявки обновлять загрузку и оборот».
   Скрытый валидатор тоже будет считать по исходному снимку?
5. `in_progress_count` освобождается по истечении `latency_sec`, или в рамках
   одной очереди только растёт?
6. `daily_approved_amount` увеличивать только по `approved`, или резервировать
   сразу при выборе провайдера?
7. Поля, которые «полезно добавить самим» (`volume_share_pct`,
   `requests_per_minute_limit`, `daily_turnover_min/max`) — класть в свой конфиг
   или дописывать в `providers.json`? Скрытый валидатор будет читать наш
   `providers.json` или свой эталонный?
8. К `operations_queue_test.json` дадут новый снимок `providers.json`,
   или используем текущий?
9. Разрешено ли добавлять лишние поля в `attempts` и в объект решения
   (`score`, `details`, `eligible_providers`)?
10. `routing_decisions_test.json` — строго массив? (Скрипт принимает и одиночный объект.)
11. Должен ли `spacepayments` попадать в `distribution` отчёта, если у него
    `traffic_percentage: 0`?
12. `period` в отчёте — дата снимка провайдеров или дата из `created_at` заявок?

**Ответы записать в `docs/QA-ANSWERS.md`** — это прямо влияет на код, Фёдор будет
править ядро по ним.

## 3. Независимая проверка ядра (к чекпоинту 2)

Ты — вторая пара глаз. Задача не «написать тесты», а **сломать**:

- [ ] Пустая очередь, очередь из одной заявки, дубли `operation_id`.
- [ ] Заявка, под которую не подходит вообще никто → должен уйти в `spacepayments`.
- [ ] `amount` = 0, отрицательный, строкой, `null`.
- [ ] Провайдер со `status: "disabled"`, с `available_requisites: 0`,
      с `daily_amount_limit: null`.
- [ ] Битый `providers.json` (не массив, нет обязательного поля) → внятная
      ошибка, а не стектрейс.
- [ ] Битый `config/routing.yml` (неизвестная стратегия, пустые веса).
- [ ] Заявка с банком, которого нет ни у кого.

Каждый найденный баг — issue в репозитории с шагами воспроизведения.

## 4. Защита (главное, 20 отраслевых баллов + впечатление техжюри)

- [ ] Презентация на 5–7 минут. Структура, которая ложится на критерии жюри:
      1. Задача и что в ней сложного (конфликт целей, а не просто «выбрать из списка»).
      2. Архитектура: hard-constraints отдельно от soft-goals, и почему это важно.
      3. Как разрешаем конфликт целей — композитный скоринг + явный порядок политик.
         Наш приоритет: **фин. обязательства → доли → конверсия**. Пример из ТЗ:
         vipay у дневного лимита, а на payflow висит обязательство 2 млн ₽/сутки.
      4. Объяснимость: показать живой `attempts` с разложением скора.
      5. Аналитика: показать `routing_report.json` и конкретные рекомендации.
      6. Backtest: «на исторических 100 операциях наш роутинг даёт X вместо Y».
- [ ] Прогнать выступление вслух минимум дважды, с таймером.
- [ ] Подготовить ответы на очевидные вопросы жюри:
      «почему такие веса», «что если провайдер добавится завтра»,
      «как поменять правило без переписывания кода».

## 5. Стопкод — регламент (за час до конца)

Это самая дорогая процедура на хакатоне. Делаем **вдвоём**, по шагам:

1. Организаторы дают `operations_queue_test.json`.
2. Кладём его в `data/operations_queue_test.json`.
3. `rake submit` — генерирует `routing_decisions_test.json` и
   `routing_report_test.json` **в корень репозитория**.
4. Проверить глазами: количество решений == количество заявок,
   `operation_id` совпадают с новой очередью, а не со старой.
5. `rake validate FILE=routing_decisions_test.json` — прогнать валидатор.
6. Коммит и push **в main**. Убедиться, что CI зелёный.
7. Открыть GitHub в браузере, ветка main, глазами увидеть оба файла в корне.

Файл называется неправильно / лежит не в корне / не в main = **0 баллов из 40**.
Проверяем оба, вдвоём, по списку.

## Как работаем в git

- Ветки + PR, прямой push в `main` в обычной работе не делаем.
- Ветки: `docs/...`, `test/...`, `fix/...`.
- CI (GitHub Actions) гоняет тесты и валидатор организаторов на каждый PR.
- Мержим только зелёное.

`main` защищён: требуется зелёный чек `test`, force-push и удаление ветки
запрещены. У нас обоих права администратора, а `enforce_admins` выключен —
значит **в момент стопкода можно пушить сдаваемые файлы прямо в `main`,
не дожидаясь PR**. Защита нужна, чтобы случайный коммит не уронил main,
а не чтобы мешать нам в последний час.
